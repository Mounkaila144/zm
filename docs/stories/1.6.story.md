# Story 1.6: Parseur `zarma → nombre` et invariant exhaustif

## Status

Done

## Story


**As a** utilisateur du moteur,
**I want** convertir un texte zarma en nombre de façon fiable et prouvée,
**so that** je garantis l'exactitude du cœur du produit indépendamment de l'ASR.

## Acceptance Criteria

1. `parser.py` analyse un texte zarma normalisé et retourne l'entier correspondant, ou une absence de résultat explicite si le texte n'est pas un nombre valide.
2. Le parseur ne devine ni n'invente jamais un nombre à partir d'un texte non numérique (retour vide/erreur, jamais une valeur arbitraire).
3. `validator.py` exécute l'invariant `parse(generate(n)) == n` sur **toute la plage** `0`–`1 000 000` et le test passe (sur les formes validées ; les formes `unresolved` sont explicitement tracées).
4. La couverture inclut les paires de confusion connues (`hinka`/`hinza`, `iyye`/`yega`, `iddu`/`iyye`) traitées comme distinctes.
5. La CI exécute l'invariant et échoue si une forme validée le viole.

## Dev Notes

### Contexte & objectif

`parser.py` + `validator.py` closent le moteur linguistique déterministe (générateur 1.4 → normaliseur 1.5 → **parseur 1.6**). Le parseur est l'**inverse du générateur** ; l'invariant `parse(generate(n)) == n` **prouve** l'exactitude du cœur produit indépendamment de l'ASR — c'est le nœud de dérisquage de tout le projet. À la fin de cette story, le paquet `zarma_numbers` est un module autonome prouvé, convertissant nombre ↔ zarma sans GPU. [Source: prd/epic-1 — Objectif étendu] [Source: architecture.md#Architectural Patterns]

Le paquet reste **autonome** : stdlib + `PyYAML` uniquement, aucune dépendance FastAPI/ASR/DB. [Source: architecture.md#Coding Standards — « Isolation du moteur linguistique »]

### Insights des stories précédentes (déterminants ici)

- **1.4 (générateur)** : `generate(n)` compose depuis le `Lexicon` ; `1 000 000` lève `UnresolvedFormError` (`UNRESOLVED_MILLION_FORM`, million `canonical: null`) ; `10 000`/`100 000` sont composés via `zambar`. Unités : forme **isolée** au top-level (`generate(2) == "ihinka"`), forme **combinée** en multiplicateur/groupe (`zambar fo`, `zangou hinka`, `waytaci cindi gou`). Exceptions dans `exceptions.py` : `GenerationError` (base, porte `code`), `OutOfRangeError`, `UnresolvedFormError`. [Source: story 1.4 — Completion Notes]
- **1.5 (normaliseur)** : **`normalize(generate(n)) == generate(n)` est garanti** (les formes canoniques sont protégées ; la map de remplacement se réduit essentiellement à `da → nda`). Donc l'invariant `parse(normalize(generate(n))) == n` revient à parser la **sortie canonique du générateur**. `normalize -> str` (primaire), `normalize_with_trace -> NormalizationResult` (optionnel). [Source: story 1.5 — Completion Notes]
- **1.3 (lexique)** : `load_lexicon()` (cache `lru_cache`), `Lexicon` expose unités isolées/combinées, tens, connectors (`cindi`, `nda`/`da`), scales (`zangou`, `zambar`, million null). Toutes les entrées `unresolved` (validation locuteurs à venir). [Source: story 1.3 / 1.4 — Completion Notes]

### Contrat des interfaces (à respecter)

- **Interface primaire : `parse(text: str) -> int | None`** — retourne l'entier, ou `None` (absence explicite) si non numérique. C'est le contrat architecture (`parse(text: str) -> int | None`) et l'usage pipeline API (`number = parse(text)`). [Source: architecture.md#Components — Key Interfaces] [Source: architecture.md#Backend Architecture — Controller Template]
- **Divergence de source (tranchée) :** la spec §11.5 propose `parse -> ParseResult` (best/alternatives/accepted/error_code). Résolution (même approche qu'en 1.5) : `parse -> int | None` primaire ; `parse_detailed -> ParseResult` optionnel pour l'API (Epic 2). Ne pas casser le contrat `-> int | None`. [Source: specification-complete-application-nombres-zarma.md#11.5] [Source: architecture.md#Components]
- `validate_invariant(range) -> Report`. [Source: architecture.md#Components — Key Interfaces]

### Grammaire du parseur (référence)

```text
0..9       → unité
10..99     → dizaine [cindi unité]
100..999   → zangou [multiplicateur] [nda reste_0_99]
1 000..999 999
           → zambar multiplicateur_1_999 [nda reste_0_999]
1 000 000  → forme spéciale (million) — NON RÉSOLUE
```
Pseudo-EBNF :
```ebnf
number         = zero | under_hundred | under_thousand | thousands | million ;
zero           = "yaamo" ;
under_hundred  = unit | ten | ten, "cindi", unit_combined ;
under_thousand = hundred_group | hundred_group, group_connector, under_hundred ;
hundred_group  = "zangou" | "zangou", unit_multiplier ;
thousands      = "zambar", multiplier_under_thousand
               | "zambar", multiplier_under_thousand, group_connector, remainder_under_thousand ;
group_connector = "nda" | validated_variant ;
```
[Source: specification-complete-application-nombres-zarma.md#11.2] [Source: specification-complete-application-nombres-zarma.md#11.3]

**Reparse des exemples du générateur (tests)** :

```text
"zangou hinza nda wayiyye cindi hinka"                           → 372
"zambar iwey cindi hinka nda zangou hinza nda waytaci cindi gou" → 12345
```
[Source: specification-complete-application-nombres-zarma.md#12]

### Codes d'erreur du parseur (référence)

`EMPTY_INPUT`, `UNKNOWN_TOKEN`, `INVALID_TOKEN_ORDER`, `MISSING_MULTIPLIER`, `DUPLICATE_SCALE`, `OUT_OF_RANGE`, `AMBIGUOUS_EXPRESSION`, `NON_NUMERIC_SPEECH`, `UNRESOLVED_MILLION_FORM`. [Source: specification-complete-application-nombres-zarma.md#11.6]

### Paires de confusion (AC4) — à garder distinctes

`hinka` (2) ≠ `hinza` (3) · `iyye` (7) ≠ `yega` (9) · `iddu` (6) ≠ `iyye` (7). Ces formes proches ne doivent **jamais** être rapprochées ni confondues par le parseur. Aucune distance de Levenshtein pour décider. [Source: prd/epic-1 — Story 1.6 AC4] [Source: specification-complete-application-nombres-zarma.md#10.1] [Source: specification-complete-application-nombres-zarma.md#7.1]

### Invariant exhaustif & CI (AC3, AC5)

- L'invariant vérifie `parse(normalize(generate(n))) == n` pour `n ∈ [0, 1 000 000]`. [Source: architecture.md#Testing Strategy — Test Examples]
- **Formes `unresolved`** (générateur lève `UnresolvedFormError`, ex. `1 000 000`) : **tracées**, pas comptées comme échec. [Source: prd/epic-1 — Story 1.6 AC3]
- **Échec CI** si une forme **produite** par le générateur est mal reparsée (violation réelle du roundtrip). [Source: prd/epic-1 — Story 1.6 AC5]
- Exécution en CI : le job `backend` lance déjà `pytest packages/zarma_numbers` ; conforme à l'architecture, prévoir l'étape dédiée `pytest .../test_invariant.py` et la cible `make invariant`. La plage complète peut être **chunkée/paramétrée** pour rester raisonnable en CI. [Source: architecture.md#CI/CD Pipeline] [Source: architecture.md#Testing Strategy — `@pytest.mark.parametrize("n", range(0, 1_000_001, 1))`]

Codes d'erreur via `ParseError` : `EMPTY_INPUT`, `NON_NUMERIC_SPEECH`, `UNKNOWN_TOKEN`, `INVALID_TOKEN_ORDER`, `MISSING_MULTIPLIER`, `DUPLICATE_SCALE`. (AC2)

Pour chaque n : `generate` → si `UnresolvedFormError` = tracé `unresolved` ; sinon `parse(normalize(generate(n)))` comparé à n → `ok` / `ambiguous` (n>resolved_max) / `violations` (n≤resolved_max). CLI `python -m zarma_numbers.validator` (exit 1 si violation). (AC3)
- **⚠️ DÉCISION MAJEURE — ambiguïté du système numérique** : la grammaire est **prouvée ambiguë pour n ≥ 100 000**. Le multiplicateur des milliers avec centaines contient un `nda` interne qui entre en collision avec le séparateur multiplicateur/reste : ex. `generate(100 005)` et `generate(105 000)` produisent **tous deux** `"zambar zangou nda gou"`. Aucun parseur ne peut lever cette ambiguïté (une chaîne → deux nombres). C'est cohérent avec les grandes échelles (`100 000`, `1 000 000`) marquées **`unresolved`** dès 1.2/1.3. → L'invariant est **enforcé** sur la plage **résolue non ambiguë `0`–`99 999`** (M avec t<100 n'a jamais de `nda` interne — `below_100` utilise `cindi`) et **trace** `100 000`–`1 000 000` (891 collisions + million). **Zéro violation** dans la plage résolue. À remonter au PO/SM : la forme canonique des grandes échelles reste à trancher (validation locuteurs, cf. 1.2).
