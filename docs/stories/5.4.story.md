# Story 5.4: Sélection du modèle du MVP

## Status

Aprouved

## Story

**As a** responsable produit,
**I want** choisir le modèle sur des données,
**so that** la décision est ancrée dans des preuves reproductibles.

## Acceptance Criteria

1. CTC et LLM sont comparés sur l'Exact Number Accuracy en conditions calme et bruit modéré (locuteurs non vus).
2. La décision documentée retient le modèle du MVP avec justification chiffrée et matrice de confusions à l'appui.
3. Les objectifs de bêta (≥ 95 % calme, ≥ 90 % bruit modéré) sont évalués et l'écart éventuel est documenté avec plan.
4. La configuration par défaut de l'API pointe vers le modèle retenu.

## Dev Notes

### Contexte & objectif

Quatrième story du track **Benchmark/ML** (Epic 5). Elle ne produit **presque aucun code** : elle
**exécute** le harnais de la story 5.2 avec les recognizers réels de la story 5.3, sur le corpus de
la story 5.1, puis **tranche** le choix CTC vs LLM du MVP et propage cette décision dans la
configuration et la documentation. C'est le point où le projet remplace une hypothèse par une
mesure. [Source: docs/prd/epic-5] [Source: architecture.md#External APIs — Meta Omnilingual ASR]

> **Gate GPU (bloquant)** : contrairement aux stories 5.1 et 5.2, celle-ci **ne peut pas** être
> réalisée sans la ressource GPU — elle exige deux passes d'inférence réelle. Elle est donc gatée par
> la décision de ressource GPU (risque n°1) **et** par la livraison de la story 5.3. Tant que ce
> n'est pas en place, l'API reste en `ASR_MODE=mock`. [Source: docs/prd/epic-5 (intro)] [Source: docs/stories/5.3.story.md#Gate GPU]

### Dépendances

| Dépendance | Statut | Ce qu'elle fournit |
|---|---|---|
| **5.1** | Done | Corpus étiqueté + manifest JSONL versionné, split strict par locuteur (`test` / `dev`), tags `short` / `long` / `confusion`. |
| **5.2** | Draft | Harnais `scripts/bench/run_benchmark.py` : Exact Number Accuracy, matrice de confusions, taux rejet / fausse acceptation, latence ASR, rapports `.json` + `.md`, mode rejeu. |

### Critères de décision (dans cet ordre)

1. **Exact Number Accuracy** sur le split `test` (locuteurs non vus), en **calme** puis en **bruit
   modéré** — critère principal. [Source: docs/prd/epic-5 — story 5.4 AC1]
2. **Taux de fausse acceptation** — un modèle qui accepte un nombre faux est plus coûteux qu'un
   modèle qui demande une répétition : le produit est délibérément prudent (FR13/FR21). [Source: architecture.md#Coding Standards — « Jamais de nombre inventé »] [Source: docs/prd/requirements.md#FR13]
3. **Matrice de confusions** — un modèle dont les erreurs se concentrent sur des paires connues
   (`asr_confusions`) est plus corrigeable en 5.5 qu'un modèle à erreurs diffuses. [Source: docs/prd/epic-5 — story 5.5 AC2]
4. **Latence ASR** (`p50` / `p95`) et contrainte de coût GPU — critère secondaire, départage à
   qualité comparable. [Source: docs/prd/requirements.md#NFR1]

### Objectifs de bêta à évaluer (NFR2)

- **≥ 95 %** Exact Number Accuracy — nouveaux locuteurs, environnement **calme**.
- **≥ 90 %** Exact Number Accuracy — nouveaux locuteurs, **bruit modéré**.

Ces objectifs sont explicitement « à ajuster après benchmark » dans le PRD : si l'écart est
documenté avec un plan, la story est satisfaite — l'objectif n'a pas à être atteint pour clore la
story, il doit être **mesuré et traité**. [Source: docs/prd/requirements.md#NFR2] [Source: docs/prd/epic-5 — story 5.4 AC3]

### Contraintes techniques clés

- **Bascule par configuration seulement (NFR9)** : `ASR_MODE` + `ASR_ENDPOINT_URL` ; aucun code API,
  aucun code mobile touché par le choix du modèle. [Source: architecture.md#Coding Standards]
- **CI et dev restent en `mock`** : le défaut du code (`Settings.ASR_MODE = "mock"`) ne change pas —
  sinon la CI sans GPU et le développement local cassent. [Source: architecture.md#CI/CD Pipeline] [Source: services/api/app/config.py]
- **Secrets hors Git (NFR3)** : `ASR_ENDPOINT_TOKEN` jamais committé, jamais côté mobile. [Source: architecture.md#Security Requirements]
- **Split par locuteur (NFR10)** : les chiffres de décision se lisent **uniquement** sur le split
  `test` ; utiliser `dev` pour décider serait une fuite méthodologique. [Source: docs/prd/requirements.md#NFR10]
- **Sans PII (NFR6)** : le document de décision ne contient que des agrégats et des `speaker_key`
  anonymes — aucune transcription identifiante, aucun audio. [Source: architecture.md#Security Requirements]
- **Versions systématiques (NFR12)** : chaque chiffre cité est rattaché à un `model_version` et un
  `grammar_version`. [Source: architecture.md#Coding Standards]
- **Hors périmètre 5.4** : écriture/modification du harnais (5.2), implémentation des recognizers
  (5.3), calibration des poids et seuils + alimentation de la table de confusions ASR (5.5). [Source: docs/prd/epic-5]

### Testing

**Nature de la story** : mesure + décision + configuration. Aucun nouveau comportement applicatif,
donc **aucun nouveau test unitaire de logique métier** n'est attendu. [Source: docs/prd/epic-5 — story 5.4]

**Vérifications exigées :**
- Non-régression complète en `ASR_MODE=mock` : `uv run pytest packages/zarma_numbers services/api scripts/bench` vert. [Source: architecture.md#Development Commands]
- Lint/format : `uv run ruff check .` + `uv run black --check .`. [Source: architecture.md#Tech Stack (Python tooling)]
- Cohérence de configuration : mode retenu présent dans `AVAILABLE_RECOGNIZERS`, factory résolvante,
  `GET /api/v1/models` cohérent. [Source: services/api/app/api/v1/models.py]
- **Reproductibilité** : rejeu du harnais sur les hypothèses archivées → chiffres identiques au
  document de décision. C'est le test d'acceptation réel de cette story. [Source: docs/prd/epic-5 — story 5.2 AC4]
- Les passes d'inférence réelles s'exécutent **hors CI standard** (GPU requis), comme le smoke test
  de la story 5.3. [Source: architecture.md#CI/CD Pipeline] [Source: docs/stories/5.3.story.md#Testing]
