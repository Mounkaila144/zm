# Story 3.5: Correction manuelle avec forme zarma

## Status

Done

## Story

**As a** utilisateur,
**I want** corriger facilement un nombre erroné,
**so that** je garde le contrôle et je renforce la fiabilité.

## Acceptance Criteria

1. L'écran Correction propose un clavier numérique pour saisir le bon nombre.
2. À la saisie, l'app affiche automatiquement la forme zarma canonique (via le générateur, exposé par l'API ou embarqué).
3. La correction est envoyée à `/feedback` avec le contexte (nombre proposé vs corrigé, versions).
4. Les nombres hors plage sont refusés avec un message clair.

## Dev Notes

### Contexte & objectif

Dernière story du parcours mobile (Epic 3) : quand le système se trompe, l'utilisateur **reprend
la main** via un clavier numérique, voit la **forme zarma canonique** correspondante en direct, et
sa correction est renvoyée en **feedback** (`corrected`) pour alimenter les métriques (Epic 4).
Point d'architecture clé : la forme zarma vient **exclusivement** du moteur `zarma_numbers` — via
un nouvel endpoint API (aucune duplication en Dart). [Source: architecture.md#High Level Architecture] [Source: docs/prd/requirements.md#FR16]

### Décision AC2 — forme zarma via API (pas d'embarqué)

L'AC2 dit « via le générateur, **exposé par l'API ou embarqué** ». **Choix : API.** Embarquer
`generate` en Dart dupliquerait la logique numérique du moteur, ce qu'interdit la règle
d'isolation (« aucune règle numérique dupliquée ailleurs »). Le générateur raise `OutOfRangeError`
hors `[0, 1 000 000]` — ce qui couvre nativement l'AC4. **Nouveau endpoint** :
`GET /api/v1/grammar/generate/{number}` → `{ number, zarma_text, grammar_version }`. À répercuter
dans l'architecture par l'Architect. [Source: architecture.md#Coding Standards — « Isolation du moteur linguistique »] [Source: packages/zarma_numbers — generate]

### Contraintes techniques clés

- **Isolation du moteur (NFR8/NFR14)** : forme zarma et bornes **autoritaires** = moteur via API ;
  le client ne recalcule ni ne réimplémente `generate`. [Source: architecture.md#Coding Standards]
- **Plage 0–1 000 000 (FR3)** : refus clair hors plage (AC4), validation autoritaire côté générateur. [Source: docs/prd/requirements.md#FR3]
- **`corrected` = saisie manuelle** ; distinct de `confirmed` (sélection candidat, 3.4). [Source: architecture.md#Data Models — Feedback]
- **Debounce** des appels générateur pour éviter de spammer l'API à chaque frappe. [Source: architecture.md#Performance Optimization — Frontend]
- **Feedback non bloquant / anonymat** : `anon_id`, aucune PII, échec gracieux. [Source: architecture.md#Error Handling Strategy] [Source: architecture.md#Authentication and Authorization]
- **Hors périmètre 3.5** : parcours mobile complet désormais couvert (3.1→3.6) ; collecte consentie
  = Epic 4. [Source: docs/prd/epic-3]
