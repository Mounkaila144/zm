## Dev Notes

### Contexte & objectif

Story du track Mobile consultable **indépendamment** du flux de reconnaissance live : elle
affiche l'historique des reconnaissances de l'utilisateur via l'endpoint `/history` (livré en
2.6). C'est une lecture seule, idéale pour paralléliser — elle ne dépend que de la fondation
3.1 et de l'API Epic 2. [Source: docs/prd/epic-3] [Source: architecture.md#API Specification — /history]

### Dépendances (toutes créées)

- **3.1 (Approved)** : fondation Flutter, route `/history`, `ApiClient` dio, `anonIdProvider`,
  arborescence `features/history/`. [Source: docs/stories/3.1.story.md]
- **API `/history` (story 2.6, créée)** : `GET /api/v1/history?anon_id&limit` → liste de
  `RecognitionResponse` triée `created_at DESC`, filtrée par `anon_id`. [Source: architecture.md#API Specification — /history] [Source: docs/stories/2.6.story.md]

### Contrat `/history`

```
GET /api/v1/history?anon_id=<uuid>&limit=<int, défaut 50>
200: [ RecognitionResponse, ... ]   # uniquement cet anon_id
```

Chaque élément porte `recognized_number`, `zarma_text`, `normalized_text`, `confidence`,
`decision`, `model_version`, `grammar_version`, `created_at`. L'écran affiche a minima
**nombre + forme zarma + date**. [Source: architecture.md#API Specification — /history] [Source: architecture.md#Data Models — Recognition]

### Modèle Dart

```dart
class RecognitionResult {
  final int? recognizedNumber;
  final String zarmaText;      // forme canonique
  final String normalizedText;
  final double confidence;
  final Decision decision;     // accept | confirm | repeat
  final List<Candidate> alternatives;
  final String modelVersion;
  final String grammarVersion;
}
```

[Source: architecture.md#Data Models — Recognition (Dart interface)]

### Contraintes techniques clés

- **Anonymat / isolation (NFR7)** : n'afficher que l'historique de l'`anon_id` local ; l'API
  garantit déjà l'isolation côté serveur. [Source: architecture.md#Authentication and Authorization]
- **Pas de logique numérique côté client** : affichage seul ; `zarma_text` et `recognized_number`
  viennent de l'API. [Source: architecture.md#Coding Standards]
- **`autoDispose`** pour libérer le provider quand l'écran est quitté. [Source: architecture.md#Frontend Architecture — State Management Patterns]
- **Hors périmètre 3.6** : détail d'une reconnaissance, relance depuis l'historique (non requis
  au MVP). [Source: docs/prd/epic-3]

  (`lib/screens/`, `lib/network/`, `lib/config/`) et non `features/history/`. Le code suit la
  structure existante : data → `lib/history/`, modèle → `lib/models/`, widget partagé →
  `lib/widgets/`.
- **Éléments supposés livrés par 3.1 mais absents** — créés dans cette story : `anonIdProvider`
  (`lib/config/anon_id.dart`, UUID v4), modèle `RecognitionResult` (`lib/models/`), widget
  partagé `ZarmaNumberDisplay` (`lib/widgets/`).
- **Contrat `/history` complété** : `HistoryRecognitionResponse` étend le contrat live avec
  `created_at` issu de la ligne persistée. La réponse `/recognize` reste inchangée; l'écran
  Historique peut désormais satisfaire réellement l'AC1 nombre + forme zarma + date.

  durable de l'identifiant relève d'une story de fondation dédiée, hors périmètre 3.6.
- **États & robustesse** : `AsyncValue.when` → indicateur (`history-loading`), message + bouton
  `Réessayer` (`ref.invalidate(historyProvider)`), vide (`history-empty`), liste
  (`history-list`). Le test de réessai prouve un second fetch puis le rendu de la liste.
  Erreurs réseau normalisées via `normalizeNetworkFailure` (messages sans détail interne).
  `autoDispose` libère le provider à la sortie de l'écran.
- **Aucune logique numérique côté client** : `recognizedNumber`/`zarmaText` viennent de l'API.
- **Checklist DoD BMAD** : 21/21 éléments applicables réussis; couverture chiffrée, nouvelles
