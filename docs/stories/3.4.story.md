# Story 3.4: Confirmation en cas d'ambiguïté

## Status

Done
## Story

**As a** utilisateur,
**I want** confirmer parmi des propositions quand le système hésite,
**so that** j'évite une erreur sans avoir à tout ressaisir.

## Acceptance Criteria

1. Quand la réponse demande confirmation, l'app présente le(s) candidat(s) ordonné(s).
2. L'utilisateur peut sélectionner un candidat, demander à répéter, ou passer en correction manuelle.
3. Le choix de l'utilisateur est renvoyé comme feedback à l'API.
4. Quand la réponse demande répétition (phrase non numérique / trop incertaine), l'app invite à réenregistrer avec un message compréhensible.

attend un choix; `repeat` ne présente aucun nombre comme résultat et invite à parler de nouveau.

ni forme zarma. [Source: architecture.md#reconnaissance-dun-nombre-chemin-nominal--ambiguïté--erreur]

### Contrat `/feedback` réel

#### Requête

```http
POST /api/v1/feedback
Content-Type: application/json
```

```json
{
  "recognition_id": "uuid de RecognitionResult.id",
  "anon_id": "uuid du provider courant",
  "feedback_type": "confirmed | corrected | rejected | repeat_requested",
  "proposed_number": 42,
  "corrected_number": null
}
```

Les deux UUID et `feedback_type` sont obligatoires dans l'implémentation Pydantic réelle; les
deux nombres sont nullables. Le serveur cherche la reconnaissance par `id` **et** `anon_id`.
Inconnu ou propriété d'un autre `anon_id` produit le même `404 RECOGNITION_NOT_FOUND`.
[Source: services/api/app/api/v1/feedback.py — `FeedbackRequest`]
[Source: services/api/app/db/repositories.py — `FeedbackRepo.save`]

#### Réponse `201`

```json
{
  "id": "uuid feedback",
  "recognition_id": "uuid reconnaissance",
  "anon_id": "uuid anonyme",
  "feedback_type": "confirmed",
  "proposed_number": 42,
  "corrected_number": null,
  "model_version": "mock-1.0.0",
  "grammar_version": "1.0.0",
  "created_at": "2026-07-24T00:00:00Z"
}
```

`model_version` et `grammar_version` sont repris par le repository depuis la reconnaissance
persistée; le mobile ne les envoie pas. [Source: services/api/app/db/repositories.py — `FeedbackRepo.save`]

#### Mapping story 3.4

| Action | `feedback_type` | `proposed_number` | `corrected_number` |
|--------|-----------------|-------------------|--------------------|
| Sélection principale | `confirmed` | nombre sélectionné | `null` |
| Sélection alternative | `confirmed` | nombre sélectionné | `null` |
| Demander à répéter depuis `confirm` | `repeat_requested` | `recognizedNumber` nullable | `null` |
| Réenregistrer depuis `repeat` | `repeat_requested` | `recognizedNumber` nullable | `null` |
| Ouvrir Correction | aucun envoi en 3.4 | — | — |

`corrected` sera envoyé en 3.5 après saisie manuelle; `rejected` n'est associé à aucune action
de la 3.4. [Source: architecture.md#feedback]
[Source: docs/prd/epic-3-application-mobile-android-parcours-complet.md#story-35--correction-manuelle-avec-forme-zarma]

### Component Specifications

**Branche `confirm` :**

- proposition principale identifiable;
- alternatives dans l'ordre serveur, sans scores;
- actions Sélectionner, Répéter, Corriger;
- état d'envoi non bloquant, contrôles désactivés et erreur + Réessayer.

**Branche `repeat` :**

- aucun candidat présenté comme résultat;
- message bref : aucun nombre n'a pu être identifié avec assez de certitude;
- action Réenregistrer, puis feedback `repeat_requested`.

[Source: docs/prd/user-interface-design-goals.md#overall-ux-vision]

### API and Error Handling

L'endpoint est soumis au rate limit configuré et utilise l'enveloppe commune :


### Risks and Mitigations

- **Pas d'idempotence backend :** un retry après réponse `201` perdue peut dupliquer le
  feedback. Mitigation : aucune boucle automatique, contrôles verrouillés, retry explicite.
- **Pas de validation croisée backend :** l'API accepte techniquement des combinaisons
  incohérentes de type/nombres. Mitigation : modèles/actions mobiles typés et tests exacts.
- **Alternatives nullable/dupliquées :** le contrat réel autorise `number = null` et peut
  répéter la proposition principale. Mitigation : aucune sélection de null, déduplication
  stable, repli Repeat si aucun candidat exploitable.
- **`anonIdProvider` en mémoire :** une divergence d'UUID donne un `404` indifférenciable d'un
  ID inconnu. Mitigation : réutiliser strictement le provider existant; dette de persistance
  hors périmètre.
- **Baseline test concurrente :** la 3.3 rapporte encore l'échec préexistant
  `history_test.dart:192`. Ne pas modifier 3.6 dans cette story; distinguer cet échec.

### Out of Scope

- Clavier numérique, génération zarma et feedback `corrected` : story 3.5.
- Historique 3.6 et son test concurrent.
- Changement backend, idempotency key ou validation Pydantic croisée.
- Toute conservation audio.

  `confirm` sans candidat exploitable bascule sur l'invite de répétition. La
  branche `repeat` n'affiche aucun nombre et propose Réenregistrer.
- Mapping feedback : sélection (principale ou alternative) → `confirmed` +
  `proposed_number` sélectionné + `corrected_number = null` ; Répéter/Réenregistrer
  → `repeat_requested` + `proposed_number = recognizedNumber` (nullable). Aucun
  `corrected` ni `rejected` en 3.4.
- Présentation typée `ConfirmedResult` : Résultat affiche le nombre/forme retenus
  sans muter la décision serveur `confirm` en faux `accept` ; la route `result`
  accepte désormais soit un `RecognitionResult` (accept), soit un `ConfirmedResult`.
- Route `correction` déplacée dans `onGenerateRoute` avec validation typée du
  `RecognitionResult` (écran sûr sinon) ; le tap Corriger n'envoie aucun feedback.
  Le bouton Corriger de Résultat passe désormais aussi la reconnaissance.
- Navigation : `confirmed` → Résultat (pushReplacement) ; `repeat_requested` →
  `popUntil` Enregistrement s'il est dans la pile, sinon Accueil, sans repasser
  par Traitement/Confirmation.
- **Manuel en attente (Task 10.2)** : la vérification interactive sur
  émulateur/appareil (envoi non bloquant, double tap, retry, boucle de
  navigation) n'a pas pu être exécutée dans cet environnement sans device. Elle
  reste à confirmer avant release ; l'équivalent automatisé (widget/controller
  tests) couvre ces comportements.
