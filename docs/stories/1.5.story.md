## Story

**As a** développeur,
**I want** normaliser un texte zarma brut avant analyse,
**so that** j'absorbe les variations d'orthographe et de casse sans corrompre le sens numérique.

## Acceptance Criteria

1. `normalizer.py` normalise casse, espaces, connecteurs et orthographes alternatives connues vers des formes canoniques.
2. La normalisation s'appuie sur la table de variantes linguistiques (jamais sur du fuzzy matching décisionnel).
3. La normalisation est idempotente (`normalize(normalize(x)) == normalize(x)`).
4. Des tests couvrent variantes orthographiques, connecteurs et entrées non numériques.

## Dev Notes

### Contexte & objectif

`normalizer.py` est le 2ᵉ module de conversion (générateur 1.4 → **normaliseur 1.5** → parseur 1.6). Il prend un texte zarma **brut** (issu de l'ASR ou saisi) et le ramène à une forme **canonique normalisée** que le parseur (1.6) pourra analyser de façon déterministe. Il absorbe les variations de casse, d'espaces et les variantes orthographiques **connues et validées**, sans jamais deviner ni corrompre le sens numérique. [Source: prd/epic-1 — Story 1.5] [Source: specification-complete-application-nombres-zarma.md#10]

Le paquet `zarma_numbers` reste **autonome** : stdlib + `PyYAML` uniquement, aucune dépendance FastAPI/ASR/DB. [Source: architecture.md#Coding Standards — « Isolation du moteur linguistique »]

### Insights des stories précédentes

- **1.3** : le `Lexicon` expose `linguistic_variant_map()` (variantes linguistiques → forme canonique) **et** `asr_confusions` — **deux accès distincts, jamais fusionnés**. Le normaliseur consomme **uniquement** `linguistic_variant_map()`. [Source: story 1.3 — Completion Notes]
- **1.4** : `load_lexicon()` est mis en cache (`lru_cache`) au niveau paquet ; `generate()` exposé ; exceptions `GenerationError`/`OutOfRangeError`/`UnresolvedFormError` dans `exceptions.py`. Le normaliseur suit la même discipline (source unique = `Lexicon`, rien en dur). [Source: story 1.4 — Completion Notes]
- Toutes les entrées du lexique sont `unresolved` (validation locuteurs à venir) — sans impact sur la mécanique de normalisation, qui applique les variantes telles que déclarées. [Source: story 1.3 — Completion Notes]

### Contrat de l'interface (à respecter)

- **Interface primaire : `normalize(text: str) -> str`** (idempotente). C'est le contrat de l'architecture (`normalize(text: str) -> str`) et l'usage du pipeline API (`text = normalize(asr.text)` puis `parse(text)`). L'idempotence `normalize(normalize(x)) == normalize(x)` n'a de sens que si `normalize` retourne une **chaîne**. [Source: architecture.md#Components — Key Interfaces] [Source: architecture.md#Backend Architecture — Controller Template]
- **Divergence de source à trancher (tranchée ici) :** la spec §11.4 évoque `normalize(text) -> NormalizationResult`. Résolution : garder `normalize -> str` comme interface primaire (conforme architecture + idempotence + pipeline) ; fournir la **trace** via une fonction séparée optionnelle (`normalize_with_trace`) qui, elle, retourne le détail `{raw, normalized, transformations}`. Ne pas casser le contrat `-> str`. [Source: architecture.md#Components] [Source: specification-complete-application-nombres-zarma.md#11.4]

### Règles de normalisation (référence)

Étapes attendues :
1. convertir en minuscules ;
2. supprimer ponctuation et espaces multiples ;
3. normaliser apostrophes et caractères Unicode ;
4. remplacer les variantes **linguistiques validées** par leur forme canonique ;
5. **séparer** les erreurs ASR des variantes linguistiques (ne pas traiter les `asr_confusions` ici) ;
6. **ne pas corriger aveuglément** les mots proches (pas de Levenshtein décisionnel) ;
7. produire (optionnellement) une trace des transformations.

[Source: specification-complete-application-nombres-zarma.md#10]

**Exemple de trace (forme cible du `NormalizationResult` optionnel)** :
```json
{
  "raw": "Zambar fo da zangu",
  "normalized": "zambar fo nda zangou",
  "transformations": [
    {"from": "da", "to": "nda", "type": "linguistic_variant"}
  ]
}
```
> Note : dans la spec, l'exemple applique aussi `zangu → zangou` comme `asr_confusion`. Ici, **le normaliseur linguistique n'applique PAS les `asr_confusions`** (séparation stricte, FR8). Si `zangu`/`zangou` est *aussi* une variante **linguistique** déclarée dans `linguistic_variant_map()`, alors ce mapping-là s'applique (type `linguistic_variant`) ; sinon `zangu` n'est pas corrigé par ce module. Suivre strictement le contenu de `linguistic_variant_map()`, ne rien inventer. [Source: architecture.md#Coding Standards — « Variantes ≠ corrections ASR »] [Source: story 1.3 — Completion Notes]

### Interdiction du fuzzy matching décisionnel (critique)

Ne jamais rapprocher un mot inconnu du mot le plus proche par simple distance de Levenshtein. `hinka` (2) et `hinza` (3) ne diffèrent que d'une lettre mais désignent des nombres différents. Le fuzzy matching pourra, plus tard et ailleurs (API), seulement *proposer des candidats* / déclencher une confirmation — **jamais** forcer un résultat. Le normaliseur, lui, ne fait que des remplacements **exacts** issus de la table de variantes. [Source: specification-complete-application-nombres-zarma.md#10.1] [Source: architecture.md#Coding Standards — NFR14]
