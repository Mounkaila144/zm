# Story 2.6: Persistance, historique et feedback

## Status

Done

## Story

**As a** responsable produit,
**I want** persister reconnaissances, historique et feedbacks,
**so that** je peux suivre la qualité et alimenter l'amélioration continue.

## Acceptance Criteria

1. La base est SQLite en dev et PostgreSQL en prod, avec migrations Alembic ; l'audio n'est jamais stocké en base.
2. Chaque reconnaissance persistée conserve au minimum `model_version` et `grammar_version`.
3. `/api/v1/history` retourne l'historique des reconnaissances d'un identifiant anonyme.
4. `/api/v1/feedback` enregistre les corrections/feedbacks utilisateur.
5. Les logs ne contiennent aucune donnée sensible ; des tests couvrent l'écriture et la relecture de l'historique et du feedback.

## Dev Notes

### Contexte & objectif

Jusqu'ici l'API `/recognize` est **stateless** (2.3→2.5 : aucune persistance). La story 2.6
introduit la **couche de données** : ORM SQLAlchemy 2.0 (async), migrations Alembic,
Repository Pattern, et les deux endpoints de suivi qualité `GET /history` et `POST /feedback`.
C'est le socle des métriques et de l'amélioration continue (Epic 4). Invariant produit
transverse : **l'audio n'est jamais stocké en base** — seules des métadonnées et du texte.
La base est **SQLite en dev** (zéro service à lancer) et **PostgreSQL en prod**, avec les
**mêmes modèles** grâce à des types portables. [Source: architecture.md#High Level Architecture] [Source: docs/prd/requirements.md#FR22]

### Insights des stories précédentes (dépendances)

**Story 2.3 — `/recognize` (Done) :** notait explicitement « Pas de persistance en 2.3 … la
base PostgreSQL et les repositories viendront en story 2.6. Ici le endpoint est stateless. »
→ c'est précisément le périmètre ici. Le handler construit déjà une `RecognitionResponse`
complète (nombre, texte, confiance, décision, alternatives, versions, latences) — il suffit
de la **persister**. [Source: story 2.3 — Dev Notes]

**Story 2.5 — Confiance & politique (Done) :** `RecognitionResponse` porte désormais un
`confidence` composite et une `decision` réelle (`accept|confirm|repeat`) + alternatives
ordonnées → ce sont ces valeurs qui sont persistées. [Source: story 2.5]

**Config existante :** `Settings.DATABASE_URL` vaut déjà `sqlite+aiosqlite:///./zarma.db`
par défaut (dev), surchargée par `.env` en prod (PostgreSQL). Aucun secret en dur. [Source: services/api/app/config.py]

**État actuel :** aucun dossier `app/db/`, aucune dépendance SQLAlchemy/Alembic installée,
`main.py` ne monte que `models`, `grammar`, `recognize`, `health`. La 2.6 crée toute la
couche persistance et monte `history` + `feedback`. [Source: services/api/app/main.py]

### Schéma cible (DDL de référence PostgreSQL — à répliquer via ORM portable)

```sql
CREATE TABLE recognitions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    anon_id         TEXT NOT NULL,
    recognized_number BIGINT,                 -- NULL si rejet/répétition
    normalized_text TEXT NOT NULL DEFAULT '',
    raw_asr_text    TEXT NOT NULL DEFAULT '',
    confidence      REAL NOT NULL,
    decision        TEXT NOT NULL CHECK (decision IN ('accept','confirm','repeat')),
    alternatives    JSONB NOT NULL DEFAULT '[]',
    model_version   TEXT NOT NULL,
    grammar_version TEXT NOT NULL,
    latency_total_ms INTEGER,
    latency_asr_ms   INTEGER,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_recognitions_anon ON recognitions(anon_id, created_at DESC);

CREATE TABLE feedbacks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    recognition_id  UUID NOT NULL REFERENCES recognitions(id) ON DELETE CASCADE,
    anon_id         TEXT NOT NULL,
    feedback_type   TEXT NOT NULL CHECK (feedback_type IN ('confirmed','corrected','rejected','repeat_requested')),
    proposed_number BIGINT,
    corrected_number BIGINT,
    model_version   TEXT NOT NULL,
    grammar_version TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_feedbacks_recognition ON feedbacks(recognition_id);
```

[Source: architecture.md#Database Schema]

**Portabilité SQLite↔PostgreSQL** : `gen_random_uuid()`, `JSONB`, `TIMESTAMPTZ` sont
spécifiques PostgreSQL. Côté ORM, utiliser les types **génériques** SQLAlchemy 2.0 :
`Uuid(as_uuid=True)` (→ CHAR(32) sur SQLite, UUID sur PG), `JSON` (→ JSON sur SQLite, JSONB
possible via variante PG), `DateTime(timezone=True)` + `server_default=func.now()`, PK
générée applicativement (`default=uuid4`) pour rester portable. [Source: architecture.md#Database Schema]

### Contrats API

**`GET /api/v1/history`** — [Source: architecture.md#API Specification — /history]
```
Query: anon_id: UUID (requis), limit: int = 50 (borné, ex. 1..200)
200: [ RecognitionResponse, ... ]   # tri created_at DESC, uniquement cet anon_id
422: validation (anon_id absent/invalide)
```

**`POST /api/v1/feedback`** — [Source: architecture.md#API Specification — /feedback] [Source: architecture.md#API Specification — FeedbackRequest]
```
Body (JSON) FeedbackRequest:
  recognition_id: UUID (requis)
  anon_id: UUID
  feedback_type: "confirmed" | "corrected" | "rejected" | "repeat_requested"
  proposed_number: int | null
  corrected_number: int | null
201: Feedback enregistré
404: recognition_id inconnu
422: validation Pydantic
```

### Écart documenté — `id` dans `RecognitionResponse`

Le schéma `RecognitionResponse` de l'architecture ne liste **pas** de champ `id`, mais
`FeedbackRequest.recognition_id` est **obligatoire** pour lier un feedback à sa reconnaissance
(relation Recognition 1→0..N Feedback). Le client obtient forcément cet id via la réponse de
`/recognize`. **Décision** : ajouter `id: UUID` à `RecognitionResponse` (champ additif,
non cassant pour les tests 2.3–2.5). À répercuter par l'Architect dans
`architecture.md#API Specification — RecognitionResponse`. [Source: architecture.md#Data Models — Recognition (`id: UUID`)] [Source: architecture.md#Data Models — « 1 Recognition → 0..N Feedback »]

### Contraintes techniques clés

- **Audio hors base (FR22/FR20)** : aucune colonne binaire audio ; l'audio de `/recognize`
  reste éphémère (décodé en 2.4, non conservé). [Source: architecture.md#Coding Standards — « Audio hors base + suppression par défaut »]
- **Versions systématiques (NFR12)** : chaque ligne `recognitions` **et** `feedbacks` porte
  `model_version` + `grammar_version`. [Source: architecture.md#Coding Standards — « Versions systématiques »]
- **Anonymat (NFR7)** : l'identité est `anon_id` (UUID device) ; l'historique ne croise jamais
  deux identifiants. Pas d'auth utilisateur au MVP. [Source: architecture.md#Authentication and Authorization]
- **Repository Pattern** : accès données via repositories (SQLAlchemy), pour rendre la
  migration SQLite→PostgreSQL transparente et le tout testable. [Source: architecture.md#Architectural Patterns — Repository Pattern]
- **Logs sans PII (NFR6)** : discipline de logs stricte ici ; l'infrastructure structlog +
  `request_id` middleware complète est traitée au durcissement (story 2.7). [Source: architecture.md#Monitoring — Logs sans PII] [Source: docs/prd/epic-2 — story 2.7]
- **Hors périmètre 2.6** : `consents`/`contributions` et l'audio consenti (Epic 4), rate
  limiting et structlog complet (story 2.7), calibration (Epic 5). [Source: docs/prd/epic-2]
