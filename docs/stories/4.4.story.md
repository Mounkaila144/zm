# Story 4.4: Retrait des contributions

## Status

Done

## Story

**As a** contributeur,
**I want** pouvoir retirer mes contributions,
**so that** j'exerce mon droit de rétractation.

## Acceptance Criteria

1. Un mécanisme permet de demander le retrait des contributions liées à un identifiant anonyme.
2. Le retrait supprime l'audio consenti et marque les métadonnées comme retirées/anonymisées.
3. Les données retirées sont exclues du dataset et des évaluations futures.

### Data Models

État final d'un consentement retiré :

```text
Consent
  anon_id        = tombstone opaque
  withdrawn      = true
  withdrawn_at   = horodatage UTC
  consent_version/accepted_at conservés pour audit non identifiant
```

État final d'une contribution retirée :

```text
Contribution
  status          = withdrawn
  audio_ref       = null
  anon_id         = tombstone opaque
  speaker_key     = tombstone opaque
  region          = null
  device_info     = null
  prompt/nombre/versions/created_at conservés
```

La FK `consent_id` peut rester : sa cible est elle-même retirée et ne contient plus
l'`anon_id` original. Les tombstones ne doivent être ni déterministes depuis l'ancien UUID,
ni journalisées, ni exposées.
[Source: architecture.md#Data Models — Consent]
[Source: architecture.md#Data Models — Contribution (Recording metadata)]
[Source: architecture.md#Database Schema]

### API Specifications

```text
POST /api/v1/recordings/withdraw
Content-Type: application/json
Body: { "anon_id": "<device UUID>" }

200: { "status": "withdrawn" }   # même réponse si déjà retiré / aucun élément
429: enveloppe RATE_LIMITED
503: enveloppe WITHDRAWAL_INCOMPLETE, réessayer
500: enveloppe INTERNAL
```

Le retrait ne dépend pas d'un consentement encore valide. Le contrat ne renvoie jamais le
nombre de lignes/fichiers, leurs IDs ni leur état antérieur.
[Source: architecture.md#API Specification — /recordings/withdraw]

### Component Specifications

Backend :

```text
withdraw(anon_id)
  -> révoquer/anonymiser les consentements + commit
  -> charger contributions non withdrawn de l'anon_id
  -> AudioStore.delete(audio_ref) pour chaque référence
  -> transaction: status withdrawn + audio_ref null + anonymisation
  -> reçu générique
```

Ce séquencement privilégie la confidentialité : dès le premier commit, aucun nouvel upload
ne peut utiliser les anciens consentements. Une interruption est réessayable, car les
fichiers absents sont acceptés et les contributions conservent l'ancien `anon_id` jusqu'à la
finalisation.

Mobile :

```text
Retirer mes contributions
  -> dialogue de confirmation
  -> annuler capture/upload + nettoyer temporaire
  -> POST /recordings/withdraw
  -> succès: vider acceptation locale -> ConsentScreen
  -> erreur: message générique + Réessayer
```

### Risks and Mitigations

- **Pas de transaction distribuée DB/filesystem :** révoquer d'abord, supprimer les fichiers,
  finaliser ensuite ; chaque phase est idempotente et réessayable.
- **Course upload/retrait :** la révocation et l'insertion utilisent le même verrou/invariant
  transactionnel sur le consentement ; aucun upload validé trop tôt ne peut committer après
  le retrait.
- **Échec partiel de suppression :** réponse `503`, consentement déjà invalide, retry sûr ;
  aucune anonymisation finale tant que toutes les suppressions n'ont pas réussi.
- **Commit final échoué après suppression :** les fichiers manquants sont acceptés au retry,
  qui peut terminer les tombstones.
- **Endpoint fondé sur un UUID non secret :** conforme au MVP sans authentification, mais
  toute personne connaissant l'UUID peut demander le retrait. Ne jamais l'exposer/loguer ;
  une authentification renforcée relève d'une évolution d'architecture.
- **Sauvegardes :** l'architecture prévoit des backups mais aucune politique de purge liée
  au retrait. Le code couvre le stockage actif ; la procédure de sauvegarde doit être
  définie avant production.

### Out of Scope

- Restauration d'une contribution retirée : interdite.
- Validation/rejet et construction du dataset : 4.5.
- Métriques agrégées : 4.6.
- Authentification utilisateur ou preuve supplémentaire au-delà de l'UUID MVP.
- Purge physique des sauvegardes historiques, qui nécessite une politique d'exploitation.
