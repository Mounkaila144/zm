# Story 3.1: Fondation de l'app Flutter et navigation

## Status

Done

## Story

**As a** développeur,
**I want** une app Flutter initialisée avec navigation et configuration API,
**so that** j'ai un socle mobile prêt à accueillir les écrans.

## Acceptance Criteria

1. `apps/mobile` est un projet Flutter Android buildable avec la solution de gestion d'état retenue par l'Architect (Riverpod ou Bloc).
2. La navigation entre les écrans principaux (Accueil, Enregistrement, Traitement, Résultat, Confirmation, Correction, Historique) est en place.
3. L'URL de l'API et la configuration proviennent d'une config non secrète ; aucun secret n'est embarqué.
4. Un client HTTP (`dio`) est configuré avec gestion des timeouts et des erreurs réseau.
5. L'app démarre sur l'écran Accueil avec le bouton micro visible.

## Dev Notes

### Contexte et objectif

Cette story transforme `apps/mobile`, actuellement présent dans l'arborescence cible comme
application Flutter Android, en socle exécutable. L'application mobile est une couche distincte
de l'API FastAPI et du service ASR ; cette story ne porte aucune logique linguistique ni ASR.
[Source: architecture/source-tree.md#unified-project-structure]

Le socle doit permettre aux stories 3.2 à 3.6 d'ajouter les comportements métier sans
réorganiser le bootstrap, la navigation, la configuration ou le client HTTP.

### Previous Story Insights

La dernière story rédigée, 2.6, a encore le statut `Aprouved` et ne contient aucun Completion
Note du Dev Agent. Il n'existe donc pas de handoff précédent validé `Done` sur lequel s'appuyer.
La demande explicite de démarrer l'Epic 3 constitue l'override du workflow. La story 3.1 reste
techniquement développable de manière autonome parce qu'elle ne consomme pas encore les
endpoints métier. [Source: docs/stories/2.6.story.md#status]

### Stack frontend imposée

- Flutter 3.24.x stable et Dart 3.5.x. [Source: architecture/tech-stack.md#tech-stack]
- Material 3 pour les composants UI accessibles. [Source: architecture/tech-stack.md#tech-stack]
- Riverpod 2.5.x pour l'état et l'injection de dépendances. Le choix Riverpod est déjà tranché
  par l'Architect ; Bloc n'est pas une option ouverte pour cette implémentation.
  [Source: architecture/tech-stack.md#tech-stack]
- `dio` 5.x pour les appels HTTP, timeouts et erreurs réseau.
  [Source: architecture/tech-stack.md#tech-stack]
- `flutter_test` et `mocktail` 1.x pour les tests frontend.
  [Source: architecture/tech-stack.md#tech-stack]

### Component Specifications

L'architecture impose Material 3, Riverpod et l'absence de logique métier/async dans les
widgets. Elle ne fournit pas de spécification de composants, de propriétés ou de design
détaillé pour les sept écrans. Dans cette story, chaque écran peut donc rester un scaffold
minimal portant son identité et les actions de navigation nécessaires ; seul l'Accueil doit
présenter le bouton micro visible. [Source: architecture/tech-stack.md#tech-stack]
[Source: architecture/coding-standards.md#critical-fullstack-rules]

### State Management

Le root de l'application est sous `ProviderScope`. La configuration et le client Dio sont des
dépendances injectables. Aucun widget ne lit directement l'environnement, ne construit son
propre client réseau ou ne porte une opération async métier. Les providers suivent le suffixe
`Provider`. [Source: architecture/coding-standards.md#critical-fullstack-rules]
[Source: architecture/coding-standards.md#naming-conventions]

### Data Models

Aucun modèle de données frontend spécifique à la story 3.1 n'est défini dans les shards
d'architecture disponibles. Ne pas dupliquer les schémas backend ni introduire des modèles de
reconnaissance avant la story qui consommera leur contrat.

### API Specifications

L'architecture sélectionne REST/OpenAPI 3.0 pour le contrat mobile↔API et `dio` pour le client,
mais les shards présents ne contiennent pas les schémas de requête/réponse frontend détaillés.
La story 3.1 configure seulement le client et sa base URL ; aucun appel métier n'est requis.
[Source: architecture/tech-stack.md#tech-stack]

La configuration doit être centralisée, non secrète et injectable. Aucun secret ou token ASR
ne peut être embarqué dans Flutter ; les secrets restent côté serveur. Les erreurs présentées
aux couches UI ne doivent pas exposer de trace ou de donnée interne.
[Source: architecture/coding-standards.md#critical-fullstack-rules]
[Source: architecture/coding-standards.md#security-requirements]

### File Locations

L'architecture fixe les frontières suivantes :

```text
apps/mobile/
├── android/
├── lib/
├── test/
└── pubspec.yaml
```

[Source: architecture/source-tree.md#unified-project-structure]

Les shards ne fournissent pas de `frontend-architecture.md` ni d'arborescence détaillée sous
`lib/`. Le développeur doit garder les fichiers de bootstrap, navigation, configuration,
réseau et écrans sous `apps/mobile/lib/`, avec les tests sous `apps/mobile/test/`, puis
documenter l'organisation retenue sans déplacer d'autres composants du monorepo.
[Source: architecture/source-tree.md#unified-project-structure]

### Navigation

Sept destinations sont requises par l'epic : Accueil, Enregistrement, Traitement, Résultat,
Confirmation, Correction et Historique. Aucun package de routing tiers n'est sélectionné dans
la stack d'architecture. Ne pas ajouter une dépendance de navigation sans nécessité documentée ;
les primitives Flutter suffisent au périmètre de fondation. [Source: architecture/tech-stack.md#tech-stack]

### Testing Requirements

**Emplacement :** `apps/mobile/test/`. [Source: architecture/source-tree.md#unified-project-structure]

**Frameworks :** `flutter_test` et `mocktail` 1.x. [Source: architecture/tech-stack.md#tech-stack]

**Commandes de référence :**

```bash
cd apps/mobile
flutter analyze
flutter test
flutter build apk --debug
flutter run
```

[Source: architecture/coding-standards.md#development-commands]

Les tests doivent rester déterministes et hors réseau : remplacer la config et le client par
des providers de test, vérifier le démarrage, les transitions entre destinations, la présence
du bouton micro et la classification des erreurs Dio. Aucun device réel n'est requis pour
3.1 ; les vérifications audio sur device commencent en 3.2.
[Source: architecture/tech-stack.md#tech-stack]

### Technical Constraints

- Android est la seule plateforme MVP prévue dans l'arborescence mobile.
  [Source: architecture/source-tree.md#unified-project-structure]
- Aucune logique métier ou async dans les widgets ; utiliser Riverpod.
  [Source: architecture/coding-standards.md#critical-fullstack-rules]
- Aucun secret embarqué ; configuration non secrète seulement.
  [Source: architecture/coding-standards.md#security-requirements]
- Pas de WebView pour du contenu distant. [Source: architecture/coding-standards.md#security-requirements]
- La stack documentée est Flutter 3.24.x / Dart 3.5.x. Le poste courant expose
  Flutter 3.44.7 / Dart 3.12.2 : cet écart doit être résolu ou accepté explicitement avant de
  générer/verrouiller des artefacts dépendants du SDK. [Source: architecture/tech-stack.md#tech-stack]

### Project Structure Notes

- `apps/mobile` existe mais ne contient actuellement qu'un `README.md` de placeholder ; aucun
  `pubspec.yaml`, `lib/`, `test/` ou `android/` n'est encore présent.
- La structure cible `apps/mobile/{lib,test,android,pubspec.yaml}` est cohérente avec
  l'architecture. [Source: architecture/source-tree.md#unified-project-structure]
- Conflit documentaire : la configuration BMAD indique une architecture shardée v4 et le
  workflow attend notamment `index.md`, `frontend-architecture.md`, `components.md`,
  `core-workflows.md`, `data-models.md` et `testing-strategy.md`, mais seuls
  `coding-standards.md`, `tech-stack.md` et `source-tree.md` sont disponibles. La story
  n'invente donc ni arborescence frontend détaillée, ni routeur tiers, ni valeurs de timeout.

### Out of Scope

- Capture, permission et nettoyage audio (`record`, `path_provider`) : story 3.2.
- Appel multipart `/recognize`, traitement et résultat : story 3.3.
- Confirmation et feedback : story 3.4.
- Correction numérique et génération zarma : story 3.5.
- Chargement de l'historique : story 3.6.
