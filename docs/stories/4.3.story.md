# Story 4.3: Upload, endpoint `recordings` et stockage sécurisé

## Status

Done

## Story

**As a** responsable données,
**I want** recevoir et stocker les contributions de façon sûre,
**so that** j'alimente le dataset sans exposer de données sensibles.

## Acceptance Criteria

1. `/api/v1/recordings` reçoit les contributions consenties (audio + métadonnées) avec les mêmes contrôles de sécurité audio que `/recognize`.
2. L'audio consenti est stocké en stockage objet/répertoire sécurisé (jamais en base) ; seules les métadonnées vont en base.
3. Les contributions sont marquées « en attente de validation » avant toute intégration au dataset.
4. Les logs ne contiennent aucune donnée sensible.

### Data Models

```text
Contribution
  id: UUID
  anon_id: text
  consent_id: UUID -> consents.id
  expected_number: bigint
  expected_prompt: text
  audio_ref: text               # référence opaque, jamais audio/chemin absolu
  speaker_key: text             # stable par locuteur anonyme
  region: text?                 # optionnel
  device_info: text?            # optionnel
  status: pending|validated|rejected|withdrawn
  model_version: text
  grammar_version: text
  created_at: timestamptz
```

L'audio est une ressource filesystem/objet distincte. `audio_ref` est la seule liaison avec
la base. Les index `speaker_key` et `status` préparent respectivement la séparation par
locuteur (NFR10) et la file de validation 4.5.

### Risks and Mitigations

- **Cohérence DB/fichier sans transaction distribuée :** stockage d'abord, DB ensuite, avec
  suppression compensatoire obligatoire sur échec DB.
- **Fuite de chemin ou traversée :** clé UUID serveur, racine configurée, référence relative
  opaque, aucune reprise du nom client et aucun `audio_ref` dans la réponse/log.
- **Consentement falsifié :** lookup conjoint `consent_id + anon_id + version courante +
  withdrawn=false`, toujours côté serveur.
- **Métadonnées falsifiées :** prompt régénéré via `zarma_numbers`, version de grammaire
  vérifiée et version modèle dérivée du recognizer.
- **Upload accepté mais réponse réseau perdue :** aucune clé d'idempotence n'est définie par
  l'architecture MVP ; documenter ce risque résiduel sans inventer un contrat dans 4.3.
- **Stockage objet futur :** l'interface `AudioStore` isole le filesystem afin qu'une
  implémentation S3-compatible puisse être ajoutée sans modifier route/repository.

### Out of Scope

- Métriques : 4.6.
