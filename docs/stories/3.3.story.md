# Story 3.3: Traitement et écran Résultat

## Status

Done

## Story

**As a** utilisateur,
**I want** voir clairement le nombre compris,
**so that** j'obtiens rapidement mon résultat.

## Acceptance Criteria

1. Après enregistrement, l'app appelle `/recognize` et affiche un état de traitement avec possibilité d'annuler la requête.
2. En cas de haute confiance, l'écran Résultat affiche le nombre en chiffres et la forme zarma.
3. Les erreurs (réseau lent, timeout, échec serveur) affichent des messages clairs et des options de reprise.
4. La latence perçue est gérée (indicateur d'activité, pas de blocage de l'UI).

route Confirmation pour leur traitement en 3.4.

class AudioHandoff {

Le WAV a été validé sur Huawei VOG-L29/API 29 comme PCM 16 bits mono 16 kHz; les prises sont

`RecordingController.deleteHandoff()` est idempotent et doit être appelé dans un `finally`
après l'envoi. [Source: docs/stories/3.2.story.md#debug-log-references]
[Source: docs/stories/3.2.story.md#completion-notes-list]

**Point d'intégration à corriger :** l'implémentation actuelle de `deleteHandoff()` efface le
fichier et le champ `handoff`, mais laisse la phase `ready`; `RecordingScreen` force ensuite
`state.handoff!` dans cette phase. Le retour après succès/erreur peut donc provoquer une
exception. La 3.3 doit rendre cet invariant impossible.
[Source: apps/mobile/lib/recording/recording_controller.dart — `_deleteHandoff`]

### Contrat API réel

#### Requête

```text
POST {API_BASE_URL}/recognize
Content-Type: multipart/form-data

audio:  fichier .wav, part Content-Type audio/wav (audio/x-wav aussi accepté)
anon_id: UUID, champ de formulaire
```

`API_BASE_URL` vaut par défaut `http://10.0.2.2:8000/api/v1`; le serveur limite l'upload à
`2_000_000` octets, vérifie MIME et signature RIFF/WAVE, puis normalise en PCM16 mono 16 kHz.
[Source: apps/mobile/lib/config/app_config.dart]
[Source: services/api/app/api/v1/recognize.py — `recognize`]
[Source: services/api/app/pipeline/audio.py — `validate_and_decode`]

#### Réponse `200`

```json
{
  "id": "uuid",
  "recognized_number": 100,
  "zarma_text": "forme canonique",
  "normalized_text": "texte normalisé",
  "confidence": 0.9825,
  "decision": "accept",
  "alternatives": [
    {"number": 90, "zarma_text": "forme candidate", "score": 0.7}
  ],
  "model_version": "mock-1.0.0",
  "grammar_version": "1.0.0",
  "latency_total_ms": 50,
  "latency_asr_ms": 50
}
```

`recognized_number` et `alternatives[].number` peuvent être `null`; les autres champs sont
obligatoires. `confidence`/`score` sont dans `[0,1]`, les latences sont des entiers positifs
ou nuls et les alternatives sont déjà triées par score décroissant.
[Source: services/api/app/api/v1/recognize.py — `RecognitionResponse`]
[Source: services/api/tests/test_recognize_pipeline.py — contrats de réponse]

#### Haute confiance et décisions

Le serveur décide :

- `repeat` si aucun nombre n'est parsé;
- `confirm` si deux candidats numériques sont trop proches;
- sinon `accept` si le score atteint le seuil serveur configurable;
- sinon `confirm` ou `repeat` selon le second seuil.

Les valeurs par défaut actuelles sont `accept >= 0.80`, `confirm >= 0.50` et marge `0.15`,
mais elles sont configurables. Le mobile doit donc router sur `decision`, jamais recopier ces
seuils. [Source: services/api/app/pipeline/policy.py — `decide`]
[Source: services/api/app/config.py — `Settings`]

#### Erreur normalisée

```json
{
  "error": {
    "code": "TIMEOUT",
    "message": "Recognition processing timed out",
    "request_id": "uuid",
    "timestamp": "2026-07-24T00:00:00Z"
  }
}
```

Statuts/codes réellement possibles et pertinents :

| Cas | Statut/code | Message mobile | Reprise |
|-----|-------------|----------------|---------|
| Timeout Dio ou serveur | transport ou `504/TIMEOUT` | « Le traitement a pris trop de temps. » | Réenregistrer |
| Pas de connexion | transport | « Impossible de joindre le serveur. » | Réenregistrer / Accueil |
| Annulation utilisateur | Dio `cancel` | Aucun bandeau d'erreur | Retour Enregistrement |
| Audio/requête invalide | `400`, `413`, `422`; `AUDIO_INVALID`, `FILE_TOO_LARGE`, `VALIDATION_ERROR` | « L'enregistrement n'a pas pu être traité. » | Réenregistrer |
| Rate limit | `429/RATE_LIMITED` | « Trop de demandes. Patientez avant de recommencer. » | Accueil / réenregistrer plus tard |
| Service/API | `500/INTERNAL`, `503/SERVICE_UNAVAILABLE` | « Le service est momentanément indisponible. » | Accueil / réenregistrer |
| Certificat | transport | « La connexion sécurisée a échoué. » | Accueil |
| JSON/contrat inconnu | client | « La réponse du service est invalide. » | Réenregistrer |

Ne pas afficher `error.message` brut. Conserver `code` et `request_id` dans l'échec pour
diagnostic sûr. [Source: services/api/app/core/errors.py — `ApiError`]
[Source: apps/mobile/lib/network/api_client.dart]

### Data Models

Réutiliser et compléter `RecognitionResult`; ne pas créer un second modèle divergent. Le
modèle actuel vient de la story 3.6 et omet alternatives/latences, tandis que son parseur
convertit toute décision inconnue en `confirm`. La 3.3 doit préserver `createdAt?` pour
l'historique tout en ajoutant un parsing live strict.
[Source: apps/mobile/lib/models/recognition_result.dart]

### API / retry / nettoyage

- Timeouts mobiles actuels : connexion 10 s, envoi 30 s, réception 30 s.
  [Source: apps/mobile/lib/config/app_config.dart]
- Timeout serveur : 30 s autour de validation + ASR + persistance.
  [Source: services/api/app/api/v1/recognize.py — `TIMEOUT_SECONDS`]
- Aucun retry automatique : le serveur appelle `repo.save(...)` avant de répondre, et
  `deleteHandoff()` supprime le fichier dans `finally`. La seule reprise sûre est une nouvelle
  prise. [Source: services/api/app/api/v1/recognize.py — `_run_pipeline`]
- La réception mobile et le timeout serveur sont tous deux à 30 s : selon le transport, le
  client peut produire son propre timeout avant de recevoir le `504`. Tester et documenter,
  sans modifier arbitrairement la config dans ce draft.

### Risks and Mitigations

- **Invariant `deleteHandoff` cassé :** `ready` peut survivre avec `handoff == null`.
  Mitigation : corriger et tester dans l'intégration 3.3.
- **Timeout frontière 30 s/30 s :** le client peut masquer le `504` serveur. Mitigation :
  couvrir les deux chemins et garder un même message sûr.
- **POST non idempotent :** un retry automatique peut dupliquer la persistance. Mitigation :
  aucun retry automatique; nouvelle prise seulement.
- **`anonIdProvider` non persistant :** l'UUID change au redémarrage du conteneur/app, ce qui
  fragilise l'historique inter-session. Hors périmètre 3.3; réutiliser le provider existant et
  signaler la dette.
- **Régression préexistante hors scope :** la 3.2 rapporte `flutter test` à 49/50 à cause de
  `history_test.dart:192`. Exécuter la suite complète et distinguer ce baseline failure d'une
  régression 3.3.
- **Stories concurrentes :** 3.1 est `Ready for Review`, 3.2 est `Done` et 3.6 est
  `Ready for Review`; préserver leurs fichiers partagés et tests.
