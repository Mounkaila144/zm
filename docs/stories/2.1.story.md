## Dev Notes

### Contexte & objectif

Première story de l'Epic 2 : poser la **couche service** (FastAPI) qui exposera le moteur linguistique de l'Epic 1. On établit ici le squelette démarrable, la config par settings, la santé et la **traçabilité des versions** (`grammar_version` du lexique, recognizers disponibles) — fondation de tous les endpoints à venir (`/recognize`, `/feedback`, `/history`…). L'API est un **serveur traditionnel conteneurisé, sans GPU** ; seul l'ASR (Epic 5) est serverless. [Source: architecture.md#Backend Architecture — Service Architecture] [Source: prd/epic-2 — Objectif étendu]

L'API **dépend de `zarma_numbers`** et lit `grammar_version` depuis lui — jamais en dur. [Source: story 1.3 / 1.4 — Completion Notes] [Source: architecture.md#Coding Standards — « Versions systématiques »]

### Contrats des endpoints (extrait OpenAPI)

```yaml
/health:
  get: { responses: { '200': { description: OK } } }   # ex. { "status": "ok" }

/models:
  get:
    responses:
      '200':
        # { active: "mock", available: ["mock","ctc","llm"] }

/grammar/version:
  get:
    responses:
      '200':
        # { grammar_version: "1.0.0", validated_count: <int>, unresolved_items: ["10000","100000","1000000", ...] }
```
[Source: architecture.md#API Specification]

- `/models.active` = `settings.ASR_MODE` (défaut `mock` en dev) ; `available` = liste des recognizers connus (`mock`, `ctc`, `llm`). Les implémentations réelles arrivent en 2.2 ; ici on **liste** seulement. [Source: architecture.md#API Specification — /models] [Source: architecture.md#Environment Configuration]
- `/grammar/version.grammar_version` **provient du lexique** (`load_lexicon().grammar_version`), pas de `settings.GRAMMAR_VERSION` en dur — la source de vérité est le paquet linguistique. `validated_count`/`unresolved_items` dérivés des statuts du `Lexicon`. [Source: architecture.md#Coding Standards] [Source: story 1.3 — Completion Notes]

[Source: architecture.md#Environment Configuration] [Source: architecture.md#Coding Standards — « Config via objet settings »]

### Contraintes techniques

- **Versions systématiques** : préparer le terrain pour que toute réponse porte `model_version` + `grammar_version` (NFR12) — ici, `grammar_version` exposé via `/grammar/version`. [Source: architecture.md#Coding Standards]
- **API sans GPU** : aucune dépendance ML dans `services/api` ; l'ASR passera par l'interface `SpeechRecognizer` (story 2.2). [Source: architecture.md#Backend Architecture]
- **Nommage** : routes en kebab-case, versionnées `/api/v1/...` ; fichiers/modules snake_case ; classes PascalCase. [Source: architecture.md#Naming Conventions]
- **Isolation** : `services/api` dépend de `zarma_numbers` ; l'inverse est interdit (le paquet linguistique n'importe jamais FastAPI). [Source: architecture.md#Coding Standards]

### Completion Notes List

- **`grammar_version` réel = `1.1.0`, pas `1.0.0`.** L'exemple d'AC5/OpenAPI dans la story indiquait `1.0.0` (valeur d'origine story 1.3), mais le lexique a été bumpé à `1.1.0` en story 1.7 (ajout `dala` + `million`). Conformément au standard « source unique de vérité / jamais en dur », l'endpoint lit `load_lexicon().grammar_version` et le test asserte `body["grammar_version"] == load_lexicon().grammar_version` (non fragile) plutôt qu'une constante figée.
- **`validated_count` / `unresolved_items`** dérivés d'un énumérateur des statuts de toutes les entrées du `Lexicon` (zero, unités 1–9, dizaines 10–90, connecteurs, échelles). Toutes les entrées étant `unresolved`, `validated_count == 0` et `unresolved_items` inclut notamment les 3 grandes échelles bloquantes `10000`/`100000`/`1000000` (assertions du test).
- **Wiring workspace** : `services/api` ajouté aux `[tool.uv.workspace].members` ET au groupe `dev` racine (via `zarma-api` + source `{workspace=true}`) pour que `uv sync` l'installe en editable et fournisse fastapi/uvicorn. `httpx` + `pytest-asyncio` ajoutés au groupe dev racine pour que le `TestClient` fonctionne en CI. `pythonpath`/`testpaths` racine étendus à `services/api` pour rendre `app` importable et découvrir les tests.
- **Tests** : réalisés avec `fastapi.testclient.TestClient` (synchrone, s'appuie sur httpx) — plus robuste que l'async ici ; `pytest-asyncio` reste déclaré comme prévu par la story.
- **Config** : champs `Settings` nommés en MAJUSCULES pour coller aux variables d'env et aux références de la story (`settings.ASR_MODE`, `settings.GRAMMAR_VERSION`). `GRAMMAR_VERSION` reste purement informatif ; la vérité vient du lexique.
- **Fix incident hors périmètre** : suppression d'un import inutilisé (`parse`) dans `scripts/zarma.py` qui faisait échouer `ruff check .` (F401 pré-existant) — nécessaire pour garder la CI verte sur la branche.
- Non fait (hors AC 2.1, par design) : `Dockerfile`, `app/core/`, `app/pipeline/`, `app/db/` (stories 2.2→2.7).
