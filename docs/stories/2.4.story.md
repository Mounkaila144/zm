# Story 2.4: Validation et traitement sécurisés de l'audio

## Status

Done

## Story

**As a** responsable sécurité,
**I want** des contrôles serveur stricts sur l'audio reçu,
**so that** j'évite les fichiers malveillants et garantis un format exploitable.

## Acceptance Criteria

1. Le serveur vérifie le MIME réel, décode l'audio, et refuse les fichiers corrompus ou trop volumineux (≤ ~2 Mo).
2. L'audio est converti/normalisé en mono 16 kHz avant traitement.
3. Le fichier audio n'est jamais exécuté et est traité dans un contexte isolé.
4. Par défaut, l'audio ordinaire est supprimé après traitement (aucune conservation sans consentement).
5. Des tests couvrent un fichier valide, un fichier corrompu, un fichier trop gros et un MIME incohérent.

## Dev Notes

### Contexte & objectif

La story 2.3 a livré le pipeline `/recognize` complet, mais avec une validation audio
**volontairement basique** (taille + `content_type` déclaré). La story 2.4 durcit cette
porte d'entrée : vérification du **MIME réel**, **décodage** effectif, **refus** des fichiers
corrompus/trop gros, **conversion mono 16 kHz** avant l'ASR, isolation du traitement et
**suppression par défaut** de l'audio ordinaire. C'est le prérequis sécurité pour brancher
un ASR réel (Epic 5) sur un flux d'entrée fiable et normalisé. [Source: architecture.md#Security Requirements — Backend Security] [Source: architecture.md#Core Workflows — Reconnaissance]

### Contrat attendu du pipeline audio

```python
# services/api/app/pipeline/audio.py (structure)
import io
from dataclasses import dataclass

import numpy as np
import soundfile as sf
import soxr
from fastapi import UploadFile

TARGET_SAMPLE_RATE = 16_000
TARGET_CHANNELS = 1
TARGET_SAMPLE_WIDTH = 2  # PCM16
WAV_MAGIC = b"RIFF"        # octets 0-3
WAV_FORMAT = b"WAVE"       # octets 8-11

@dataclass
class DecodedAudio:
    pcm: bytes          # PCM16 mono 16kHz normalisé (prêt pour AudioInput.data)
    sample_rate: int    # == 16000 après conversion
    channels: int       # == 1
    duration_ms: int

async def validate_and_decode(audio: UploadFile) -> DecodedAudio:
    # 1. Filtre rapide du content_type déclaré (audio/wav, audio/x-wav) -> 422 sinon
    # 2. Lecture bornée en mémoire (<= MAX_AUDIO_SIZE + 1) -> 413 si trop gros ; 422 si vide
    # 3. Vérif MIME réel : header[0:4]==RIFF et header[8:12]==WAVE -> 400/422 si incohérent
    # 4. Décodage via soundfile depuis un BytesIO (jamais de fichier disque) :
    #       data, sr = sf.read(io.BytesIO(content), dtype="float32", always_2d=True)
    #    -> toute exception soundfile = fichier corrompu -> 400/422 (message sûr)
    # 5. Down-mix mono (numpy : data.mean(axis=1)) si channels > 1
    # 6. Ré-échantillonnage si sr != 16000 : mono = soxr.resample(mono, sr, 16000)
    # 7. Quantification PCM16 : (mono * 32767).clip(-32768, 32767).astype("<i2").tobytes()
    # 8. return DecodedAudio(pcm=..., sample_rate=16000, channels=1, duration_ms=...)
```

### Choix de la bibliothèque de décodage — DÉCISION FIGÉE

**Décision (SM + validation utilisateur, 2026-07-24) : `soundfile` + `numpy` + `soxr`.**

Le Tech Stack ne fixait aucune bibliothèque de décodage audio côté serveur ; ce choix la
complète pour la couche API (à répercuter dans `architecture.md#Tech Stack` par l'Architect).

**Rôles :**
- **`soundfile`** (libsndfile, ~1.0) : décodage WAV depuis un `BytesIO` **en mémoire** et
  **rejet propre** des fichiers corrompus/tronqués (cœur de l'AC1). Le wheel PyPI **embarque
  libsndfile** → `pip install` suffit, **aucun binaire système** requis (contrainte CI/VPS).
- **`numpy`** (>=1.26) : manipulation des échantillons et **down-mix mono** (AC2).
- **`soxr`** (~0.5) : **ré-échantillonnage haute qualité** vers 16 kHz (AC2) quand l'entrée
  n'est pas déjà en 16 kHz ; wheel léger et dédié.

**Justification (vs alternatives écartées) :**
- ❌ **stdlib `wave` + `audioop`** : `audioop` est **déprécié et retiré en Python 3.13** — à
  proscrire pour du code neuf ; ré-échantillonnage de qualité médiocre.
- ❌ **`pydub`** : dépend du **binaire `ffmpeg`** au niveau système → viole la contrainte
  « CI/VPS sans binaire système ».
- ✅ **`soundfile`/`numpy`/`soxr`** : uniquement des **wheels pip**, **sans GPU ni binaire
  système**, robustes, standard de l'écosystème audio ML, et **pérennes** (compatibles 3.11 → 3.13+),
  cohérents avec l'ASR réel Omnilingual de l'Epic 5. [Source: architecture.md#High Level Architecture — sans GPU] [Source: architecture.md#Tech Stack — Backend Language]

**Traitement en mémoire uniquement** : `soundfile` lit depuis `io.BytesIO(content)` — aucun
fichier temporaire sur disque, ce qui satisfait l'isolation (AC3) et la non-conservation (AC4).

### Mapping des erreurs (réutiliser l'`ApiError` de la 2.3)

| Cas | Statut | Code | Message (sûr) |
|-----|--------|------|----------------|
| Fichier > ~2 Mo | `413` | `FILE_TOO_LARGE` | « File too large (max 2MB) » |
| Fichier vide | `422` | `AUDIO_INVALID` | « Audio file cannot be empty » |
| MIME déclaré non autorisé | `422` | `AUDIO_INVALID` | « Invalid audio format » |
| MIME réel incohérent (contenu ≠ WAV) | `400`/`422` | `AUDIO_INVALID` | « Invalid or inconsistent audio content » |
| WAV corrompu / non décodable | `400`/`422` | `AUDIO_INVALID` | « Corrupted audio file » |

Aucun message ne doit exposer de stack trace, de détail interne, ni de contenu audio.
Toutes les erreurs internes inattendues restent capturées par le `try/except` de `recognize()`
(→ `500 INTERNAL`). [Source: architecture.md#Error Handling Strategy — Error Response Format] [Source: architecture.md#Coding Standards — « Erreurs sans fuite »]

### Contraintes techniques clés

- **Refus avant décodage complet** : la borne de taille (~2 Mo) est vérifiée **avant** de décoder
  entièrement le fichier, pour éviter tout traitement d'un payload volumineux. [Source: architecture.md#Security Requirements — Backend Security]
- **Aucune exécution du fichier** : le contenu audio est traité comme des **données inertes** —
  jamais passé à un shell, `eval`, ni interprété comme un chemin/commande. Traitement en mémoire,
  isolé. [Source: epic-2 AC3] [Source: architecture.md#Security Requirements — Backend Security]
- **Suppression par défaut** : l'audio de `/recognize` n'est **jamais** conservé (ni base, ni disque) ;
  tout buffer temporaire est libéré après traitement, y compris en erreur (`finally`). Seul l'audio
  **consenti** (stories 4.x) est stocké, hors base. [Source: architecture.md#Coding Standards — « Audio hors base + suppression par défaut »] [Source: architecture.md#Core Workflows — Reconnaissance]
- **Versions systématiques** : la conversion audio ne change pas le contrat de réponse — `model_version`
  et `grammar_version` restent présents (inchangés depuis la 2.3). [Source: architecture.md#Coding Standards — « Versions systématiques »]
- **ASR via l'interface uniquement** : la conversion produit `AudioInput` ; l'appel reste
  `recognizer.transcribe(...)` via injection. [Source: architecture.md#Coding Standards — « ASR via l'interface uniquement »]
- **Hors périmètre 2.4** : confiance composite + politique accept/confirm/repeat (story 2.5),
  persistance/historique (story 2.6), rate limiting (story 2.7), stockage audio consenti (story 4.3).
