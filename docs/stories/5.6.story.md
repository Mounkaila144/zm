## Story

**As a** ingénieur,
**I want** contraindre le décodage du modèle ASR à la grammaire des nombres zarma,
**so that** le système ne produise que des sorties valides et exploitables, avec un taux d'erreur minimal, sans dépendre d'un GPU ni d'un modèle lourd.

## Acceptance Criteria

1. Le décodage produit **exclusivement** des chaînes appartenant à la grammaire des nombres zarma (0–1 000 000), quel que soit le contenu audio : aucune sortie en écriture non latine, aucune forme orthographique hors lexique.
2. Le décodage s'appuie sur une **recherche en faisceau sur un automate/trie** de la grammaire (et non sur une énumération exhaustive), afin de couvrir l'espace complet 0–1 000 000 dans un temps compatible avec NFR1.
3. Un **mécanisme de rejet** empêche de produire un nombre lorsque l'audio ne correspond pas à un nombre : le score contraint est comparé à une référence et, au-delà d'un seuil calibré, la décision est `repeat` (FR21/NFR14).
4. Le gain est **mesuré par le harnais 5.2** sur le corpus 5.1, avec **split par locuteur** : rapport versionné comparant glouton et contraint, ventilé par condition et par tranche de nombres.
5. L'intégration respecte l'interface `SpeechRecognizer` **sans la modifier** : le décodage est interne au recognizer, aucun changement d'API publique ni de mobile (NFR9).
6. Aucun *fuzzy matching* décisionnel n'est introduit : la sélection repose sur un score acoustique sur un espace de sorties valides, jamais sur une distance d'édition textuelle (NFR14).
7. **Performance cible** : dépasser nettement la référence mesurée du prototype (73 % global / 79 % sur locuteur non vu). Tout écart aux objectifs NFR2 (≥ 95 % calme, ≥ 90 % bruit modéré) est documenté et chiffré, jamais masqué.

## Dev Notes

### Contexte & origine de la story

Cette story **n'était pas prévue au PRD**. Elle découle d'un constat expérimental établi
pendant l'Epic 5, documenté dans `docs/qa/benchmarks/exploratory-ctc-vs-llm-v1.md`.

Le pipeline officiel d'Omnilingual ASR effectue un **décodage glouton** :

```python
# omnilingual_asr/models/inference/pipeline.py, l.316-317
logits, bl_out = self.model(batch.source_seqs, batch_layout)
pred_ids = torch.argmax(logits, dim=-1)     # ← argmax trame par trame
```

Le modèle CTC émet à chaque trame une distribution sur **10 288 tokens** (dont ~1 122
latins seulement). Sur des énoncés courts — le cas d'usage central du produit — les
caractères chinois/arabes l'emportent d'un cheveu, **alors que les chemins latins
corrects existent dans les logits**. Le problème n'est donc **ni le modèle, ni l'audio,
ni la langue** : c'est la stratégie de décodage.

### Impact sur les stories existantes (à arbitrer par l'Architect / le PO)

| Story | Impact |
|---|---|
| **5.3** | Le service ASR distant reste valable, mais le **LLM 6,2 Go n'est plus nécessaire** ; l'hypothèse « GPU obligatoire » tombe. Le décodage doit être ajouté côté service. |
| **5.4** | Le choix CTC vs LLM est **largement tranché en faveur du CTC + décodage contraint** (précision, poids, coût, latence). La story reste à faire pour la mesure formelle multi-conditions. |
| **5.5** | La **table de variantes en aval devient largement inutile** : les variantes deviennent des prononciations dans le lexique de décodage. La calibration des seuils reste pertinente et doit intégrer le nouveau signal de rejet. |
| **Gate GPU** | Le blocage « décision de ressource GPU » de l'Epic 5 est **fortement atténué** : hébergement CPU scale-to-zero, voire embarqué à terme (CTC quantisé ~300–400 Mo). |

### Contraintes techniques clés (non négociables)

- **Aucun fuzzy matching décisionnel (NFR14)** : le décodage contraint est une recherche
  acoustique sur un espace de sorties valides, **pas** un rapprochement textuel. Aucune
  distance de Levenshtein ne doit intervenir dans le choix d'un nombre.
- **Jamais de nombre inventé (FR21)** : la contrainte garantit la **validité**, **pas** la
  **correction**. Sans mécanisme de rejet, un bruit produirait un nombre valide — l'AC3
  n'est pas optionnel.
- **Source unique** : grammaire et formes canoniques proviennent de `zarma_numbers`,
  jamais réécrites dans le décodeur.
- **ASR via l'interface uniquement (NFR9)** : `SpeechRecognizer` ne change pas.
- **Config via `Settings`** : aucun paramètre en dur, aucun secret.
- **CI sans GPU** : tests sur logits en fixtures.
- **Sans PII (NFR6)** : aucune transcription identifiante ni audio dans les logs/rapports.
- **Hors périmètre** : fine-tuning du modèle acoustique (piste distincte), quantisation /
  embarqué, choix formel du modèle (5.4), calibration complète des poids (5.5).

## Annexe A — Savoir vérifié sur le modèle et le décodage

### A.1 — Accéder aux logits (VÉRIFIÉ)

L'API publique `ASRInferencePipeline.transcribe()` ne renvoie que `List[str]`. Les logits
existent mais sont consommés en interne. Méthode utilisée par le prototype :

```python
from omnilingual_asr.models.inference import pipeline as P

_captured = {}
_original = P.ASRInferencePipeline._apply_model_wav2vec2asr

def _patched(self, batch):
    layout = P.BatchLayout(
        batch.source_seqs.shape,
        seq_lens=batch.source_seq_lens,
        device=batch.source_seqs.device,
    )
    logits, out_layout = self.model(batch.source_seqs, layout)
    _captured["logits"] = logits.detach().float().cpu()   # (batch, trames, vocab)
    _captured["lens"] = list(out_layout.seq_lens)
    return _original(self, batch)

P.ASRInferencePipeline._apply_model_wav2vec2asr = _patched
```

> ⚠️ Le *monkeypatch* convient à un prototype, **pas à du code de production**.
> En production, appeler `self.model(...)` directement (sans passer par `transcribe`)
> ou instancier le modèle via `model=`/`tokenizer=` (le constructeur les accepte :
> `ASRInferencePipeline(model_card=None, model=..., tokenizer=...)`).

**Formes observées** : logits `(1, T, 10288)` ; `T ≈ 34` trames pour ~0,7 s d'audio
(≈ 50 trames/seconde, soit 20 ms par trame — utile pour la contrainte de durée).

### A.2 — Tokenizer (VÉRIFIÉ)

```
VocabularyInfo(size=10288, unk_idx=3, bos_idx=0, eos_idx=2, pad_idx=1)
```

- **Taille du vocabulaire de sortie : 10 288.** Seuls **~1 122** tokens sont latins ou vides.
- Encodage : `encoder = pipe.tokenizer.create_encoder()` ; filtrer les tokens spéciaux
  bas (`> 3`). Exemple vérifié : `"afo"` → `[3859, 10104, 5262]`.
- Détokenisation : `pipe.token_decoder` (créé avec `skip_special_tokens=True`).
- Le décodage CTC officiel fusionne les répétitions consécutives (`seq[1:] != seq[:-1]`).

### A.3 — Fonction de score validée (VÉRIFIÉ)

```python
score = F.ctc_loss(
    log_probs.unsqueeze(1),          # (T, 1, V), après log_softmax
    torch.tensor([ids]),
    torch.tensor([T]),
    torch.tensor([len(ids)]),
    blank=0,                          # ← 0, PAS 1 (voir Annexe D §1)
    reduction="sum",
    zero_infinity=True,
).item() / (len(ids) ** p)            # p = 1.0 (optimum mesuré)
```

Le candidat de **score minimal** est retenu.

**Calibration de `p`** (calibré sur v1+v2, testé sur v3 tenu à l'écart — NFR10) :

| p | v1+v2 (calibration) | v3 (test, voix jamais vue) |
|---|---|---|
| 0.0 (brut) | 45 % | 52 % |
| 0.5 | 61 % | 67 % |
| **1.0** | **70 %** | **79 %** |
| 1.2 | 68 % | 67 % |
| 2.0 | 35 % | 36 % |

`p = 1.0` est un **optimum net** (le balayage a été poussé jusqu'à 2.5). Sans
normalisation, le biais du CTC vers les séquences courtes fait converger toutes les
réponses vers `afo`.

### A.4 — Référence de performance à dépasser (VÉRIFIÉ)

Corpus : **3 locuteurs, 99 fichiers**, 52 nombres distincts (0 → 10 000), condition
calme. Espace de recherche : 1010 candidats. Modèle `omniASR_CTC_300M_v2`, CPU, M1.

| Locuteur | n | Glouton | Contraint (52 cand.) | Contraint (1010 cand.) |
|---|---|---|---|---|
| v1 | 39 | 1/39 (3 %) | 30/39 (77 %) | 29/39 (74 %) |
| v2 | 27 | 1/27 (4 %) | 19/27 (70 %) | 17/27 (63 %) |
| v3 | 33 | 0/33 (0 %) | 28/33 (85 %) | 26/33 (79 %) |
| **TOTAL** | **99** | **2/99 (2 %)** | **77/99 (78 %)** | **72/99 (73 %)** |

**Robustesse à l'échelle mesurée** : ×20 de candidats (52 → 1010) ne coûte que
**5 points**. Le score acoustique discrimine réellement.

### A.5 — Mode d'échec connu (VÉRIFIÉ)

Sur les 27 erreurs restantes, **22 apparient un énoncé court à un candidat long** :

| Attendu | Obtenu |
|---|---|
| 1 (`afo`) | 222 (`zangou hinka nda waranka cindi hinka`) |
| 6 (`iddou`) | 122 (`zangou nda waranka cindi hinka`) |
| 80 (`wayhakkou`) | 282 (`zangou hinka nda wayhakkou cindi hinka`) |

Précision par tranche : `0-20` 72 %, `21-99` 62 %, `100-999` 88 %, `≥1000` 86 %.
Les nombres **courts** sont donc les plus fragiles — contre-intuitif, et c'est
précisément ce que la **contrainte de durée** devrait corriger (un extrait de 0,7 s ≈ 34
trames ne peut pas contenir six mots).

## Annexe C — Grammaire formelle des nombres (dérivée de `generator.py`)

À implémenter comme automate/trie. **Ne pas recopier ces règles en dur** : les dériver
du lexique et du générateur (source unique).

```
NUMBER      := ZERO | UNIT_ISOLATED | COMPOSED | MILLION

ZERO          := "yaamo"                                        # n = 0
UNIT_ISOLATED := afo|ihinka|ihinza|itaci|igou|iddou|iyye|ahakou|iyega    # n = 1..9 SEUL
MILLION       := "million"                                      # n = 1 000 000

# 1..99 (unités toujours en forme COMBINÉE dans ce contexte)
BELOW_100(n)  := UNIT_COMBINED                    si n < 10
               | TENS                             si n % 10 == 0
               | TENS "cindi" UNIT_COMBINED       sinon

# 1..999
BELOW_1000(n) := BELOW_100(n)                                        si n < 100
               | "zangou" [UNIT_COMBINED si n//100 > 1]
                          ["nda" BELOW_100(n%100) si n%100 > 0]

# 1 000..999 999
ABOVE_1000(n) := "zambar" BELOW_1000(n//1000)
                 ["nda" ["dala" si (n//1000)%100 == 0 et n//1000 >= 100]
                        BELOW_1000(n%1000)                     si n%1000 > 0]
```

**Points de vigilance :**

1. **Asymétrie isolée/combinée** : `1` seul = `afo` (isolée) ; `21` = `waranka cindi fo`
   (combinée). L'automate doit interdire `waranka cindi afo`.
2. **Le multiplicateur SUIT l'échelle** : `200` = `zangou hinka` (« cent deux »), pas
   l'inverse.
3. **`zangou` sans multiplicateur** vaut 100 (le `1` est implicite) ; idem `zambar fo`
   = 1000 où `fo` est explicite. Vérifier ces cas limites.
4. **`dala`** n'apparaît que dans le cas de désambiguïsation décrit ci-dessus.
5. **1 000 000** est un cas particulier (emprunt lexical), pas une composition.

Exemples canoniques de référence (vérifiés) :

```
0 yaamo · 1 afo · 11 iwey cindi fo · 20 waranka · 42 waytaci cindi hinka
99 wayyegga cindi yega · 100 zangou · 101 zangou nda fo · 200 zangou hinka
372 zangou hinza nda wayiyye cindi hinka · 1000 zambar fo
1234 zambar fo nda zangou hinka nda waranza cindi taci
10000 zambar iwey · 100000 zambar zangou · 100005 zambar zangou nda dala gou
1000000 million
```

## Annexe D — Pièges vérifiés (à ne pas refaire)

1. **`blank = 1` est FAUX.** Le tokenizer déclare `pad_idx=1`, ce qui suggère
   intuitivement `blank=1`. **Testé : effondrement à 0–21 %.** Le bon indice est
   **`blank = 0`** malgré `bos_idx=0`.
2. **Le paramètre `lang=` est ignoré par le CTC.** Vérifié : passer `lang=["dje_Latn"]`
   au modèle CTC ne change **strictement rien** à la sortie. Seul le variant LLM le
   respecte. Ne pas compter dessus pour contraindre l'écriture.
3. **Variantes orthographiques réellement observées** (utile pour les prononciations
   alternatives — à valider par un locuteur natif avant intégration) :

   | Canonique | Formes entendues |
   |---|---|
   | `iwey` | `i wey`, `i way`, `i woy`, `iwai`, `iway` |
   | `cindi` | `cinda`, `chindi`, `ci ndi`, `cinde` |
   | `iddou` | `iddu` |
   | `igou` | `i gu` |
   | `yaamo` | `yamo` |
   | `afo` | `afu` |
   | `ihinza` | `ihinzo`, `hiza` |
   | `ahakou` | `hawku`, `hakku`, `hokku` |
   | `iyega` | `yagga`, `yoga` |
   | `zangou` | `zangu`, `zongu`, `zonga` |
   | `zambar` | `zombar` |

   ⚠️ La **segmentation** (espaces) est le cas le plus fréquent : `i wey` vs `iwey`.
   Un décodeur au niveau token/caractère doit être insensible à cette variation.
4. **Ne pas exposer les logits hors du recognizer** : charge utile énorme
   (T × 10 288 flottants) et couplage contraire à NFR9.
5. **Le prototype fixe `acoustic_score = 1.0`** faute de score réel : les signaux de
   marge et de confusion de la confiance composite sont donc actuellement **inopérants**.

**Task 1 — Grammaire exploitable par un décodeur (terminée).**

- **Structure retenue : automate fini déterministe (DFA), pas un trie plat.** Un trie
  exhaustif des 1 000 001 formes est ingérable ; le DFA partage ses sous-structures et
  tient en **3 299 états / 33 tokens**, construit en ~0,03 s (AC2).
- **Dérivation par observation du générateur, aucune règle recopiée.** `_derive_forms`
  n'encode aucune règle de composition : elle *interroge* `generate()` et découpe les
  sorties par préfixe vérifié (`generate(m*1000)` → forme du multiplicateur ;
  `generate(1000+r)` → forme du reste ; `generate(m*1000+1)` → présence du marqueur
  `dala`). Toute contradiction lève `GrammarDerivationError` au lieu de deviner. Si le
  générateur ou le lexique changent, l'automate suit automatiquement.
- **Non-déterminisme réel, traité par déterminisation.** Après `zangou nda`, on peut être
  encore dans le multiplicateur (`zangou nda fo` = 101 milliers) ou déjà dans le reste
  (`zambar zangou nda gou` = 105 000). Construction NFA (3 tries greffés) puis
  sous-ensembles → DFA acyclique.
- **Preuve d'exactitude de la langue** : le comptage des chemins acceptants du DFA donne
  **exactement 1 000 001** ; combiné à l'acceptation de chaque `generate(n)` et à
  l'injectivité du générateur (invariant 1.7), cela prouve que la langue de l'automate est
  *exactement* celle du générateur — ni sur-génération (AC1), ni sous-génération.
- **Asymétrie isolée/combinée** : émerge de la dérivation (`afo` accepté seul, `fo` refusé
  seul, `waranka cindi afo` refusé). Aucun cas particulier codé.
- **Marqueur `dala`** : requis/interdit **par multiplicateur**, observé un à un ; états
  distincts dans l'automate (`zambar zangou nda dala gou` ≠ `zambar zangou nda gou`,
  `zambar fo nda dala fo` refusé).
- **Prononciations alternatives** : `pronunciations` (token canonique → orthographes) et
  `canonical_form()` font converger toutes les variantes vers la même sortie canonique
  (`zangou da fo` → `zangou nda fo`). Alimenté **uniquement** par les variantes
  linguistiques du lexique ; les `asr_confusions` ne sont jamais lues (FR8, test dédié).
  Deux protections : une variante qui est elle-même une forme canonique n'est pas réécrite
  (`fo` ≠ `afo`), et une prononciation ambiguë lève `GrammarDerivationError`.
- **Aucun fuzzy matching** (NFR14) : appartenance = parcours de transitions exactes.
  Aucune sortie non latine possible — l'alphabet est fermé sur 33 tokens ASCII.
