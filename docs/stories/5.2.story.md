# Story 5.2: Harnais d'évaluation Exact Number Accuracy

## Status

Done

## Story

**As a** ingénieur,
**I want** un harnais d'évaluation automatisé,
**so that** je compare objectivement les modèles.

## Acceptance Criteria

1. Le harnais exécute le pipeline complet (ASR → normalisation → parsing) sur le corpus et calcule l'**Exact Number Accuracy** (métrique de décision, pas le WER).
2. Il produit une **matrice de confusions** des nombres et met en évidence les paires proches.
3. Il mesure les taux de rejet / fausse acceptation et la latence ASR.
4. Les résultats sont reproductibles et exportés (rapport versionné).

### Enchaînement exact à rejouer (source unique)

Extrait de la route `/api/v1/recognize` — c'est **ce** chemin que le harnais doit exécuter, via la
fonction pure extraite en Task 1 (jamais recopié) :

```python
asr_result = recognizer.transcribe(AudioInput(data=pcm, format="pcm_s16le"))
normalized_text = zarma_numbers.normalize(asr_result.text)
number = zarma_numbers.parse(normalized_text)
numeric_candidates = numeric_candidates_from_asr(asr_result)
confidence = composite_confidence(asr=..., normalized_text=..., number=..., numeric_candidates=..., settings=...)
decision = decide(score=confidence.score, number=number, numeric_candidates=..., settings=...)
```

[Source: services/api/app/api/v1/recognize.py#_run_pipeline]

Le harnais appelle ces **fonctions** directement — **pas** l'endpoint HTTP : pas de base de données,
pas de rate limiting, pas de persistance dans un run de benchmark. [Source: architecture.md#Backend Architecture — Controller/Route Organization]

### Définitions des métriques (à implémenter telles quelles)

| Métrique | Définition |
|---|---|
| **Exact Number Accuracy** | `#(recognized_number == expected_number) / #entrées` — un rejet compte comme échec. Métrique de décision, **pas** le WER. |
| **Taux de rejet** | part de `decision == "repeat"`. |
| **Taux de fausse acceptation** | part de `decision == "accept"` **et** `recognized_number != expected_number` (y compris `None`). |
| **Taux de confirmation** | part de `decision == "confirm"`. |
| **Latence ASR** | `count / avg / p50 / p95 / min / max` sur `AsrResult.latency_ms`, distincte de la latence totale (NFR1). |
| **Matrice de confusions** | effectifs par couple `(expected_number, predicted_number \| null)` ; paires hors diagonale triées par fréquence ; marquage « paire proche » via `asr_confusions`. |

Ventilations attendues : global, par `condition` (`calme` / `bruit`), par tag (`short` / `long` /
`confusion`), par `split`. [Source: docs/prd/epic-5 — story 5.2] [Source: docs/prd/requirements.md#NFR2]

### Contraintes techniques clés

- **ASR via l'interface uniquement (NFR9)** : aucune importation de modèle dans le harnais ;
  Mock/rejeu aujourd'hui, CTC/LLM par configuration après 5.3. [Source: architecture.md#Coding Standards]
- **Aucune règle dupliquée** : normalisation, parsing, confiance et politique restent la propriété
  de `zarma_numbers` et `services/api/app/pipeline` — le harnais orchestre, il ne décide pas.
  [Source: architecture.md#Coding Standards — « Isolation du moteur linguistique »]
- **Jamais de nombre inventé / aucun fuzzy matching (FR21, NFR14)** : un texte non numérique reste
  un échec + `repeat`, jamais rapproché d'un nombre « proche ». [Source: architecture.md#Coding Standards]
- **Variantes ≠ corrections ASR (FR8)** : la mise en évidence des paires proches utilise
  `asr_confusions`, jamais la table de variantes linguistiques. [Source: architecture.md#Coding Standards]
- **Versions systématiques (NFR12)** : `model_version` + `grammar_version` dans **chaque** rapport.
  [Source: architecture.md#Coding Standards]
- **Sans PII (NFR6)** : agrégats + `speaker_key` déjà anonymes ; aucun audio, aucune transcription
  identifiante dans le rapport versionné. [Source: architecture.md#Security Requirements]
- **Split par locuteur (NFR10)** : les chiffres de décision se lisent sur le split `test`
  (locuteurs non vus) — le harnais rapporte le split évalué. [Source: docs/prd/requirements.md#NFR10]
- **CI sans GPU** : les tests du harnais tournent en Mock/rejeu. [Source: architecture.md#CI/CD Pipeline]
- **Hors périmètre 5.2** : recognizers réels (5.3), **choix** du modèle MVP (5.4), calibration des
  poids/seuils et alimentation de la table de confusions ASR (5.5). Le harnais **mesure**, il ne
  règle rien. [Source: docs/prd/epic-5]
